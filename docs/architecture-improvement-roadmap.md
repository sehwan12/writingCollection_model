# 손글손글 개선 로드맵

작성일: 2026-07-31  
대상: Flutter 클라이언트(`writingCorrection_flutter`), FastAPI 서버(`writingCollection_model`), 배포·운영 환경

## 목적과 산정 기준

현재 코드를 기준으로 확인 가능한 위험과 개선 기회를 Frontend, Backend, Infrastructure로 나누어 정리한다. 일정은 해당 코드베이스에 익숙한 개발자 1명이 구현·기본 테스트·리뷰 반영까지 수행할 때의 **순수 작업일(인일)** 추정치다. 운영 계정 발급, 디자인/정책 결정, 실제 부하 검증 대기는 별도다.

우선순위 정의:

- **P0**: 개인정보·계정·서비스 보안에 직접 영향을 주므로 배포 전 또는 즉시 처리
- **P1**: 데이터 정합성, 장애 회복, 핵심 사용 경험에 큰 영향
- **P2**: 확장성·개발 생산성·운영 품질 개선

## 요약 로드맵

| 순서 | 범위 | 핵심 결과 | 추정 |
| --- | --- | --- | --- |
| 1 | P0 보안 | 인증서 우회 제거, API 사용자 소유권 검증, CORS/비밀정보 정리 | 3~5일 |
| 2 | P1 안정성 | 평가 저장을 원자화하고 오류·재시도·사용자 피드백 표준화 | 4~7일 |
| 3 | P1 품질 기반 | API/도메인/위젯 테스트와 CI 품질 게이트 구축 | 5~8일 |
| 4 | P2 구조화 | 모듈러 모놀리스 경계 및 설정·외부 AI 어댑터 도입 | 7~12일 |
| 5 | P2 확장 | OCR 평가를 비동기 워커로 분리하고 관측성·배포 자동화 강화 | 10~18일 |

P0~P1 최소 안정화는 병렬 작업이 가능하면 약 2주, 한 명이 순차 수행하면 약 3~4주를 예상한다. 워커 분리는 실제 평가 요청량·응답 시간 측정 후 결정한다.

### Frontend 권장 완료 기준

- 릴리스 빌드에서 HTTP 및 인증서 검증 우회 코드가 없다.
- dev/staging/prod가 빌드 인자만으로 각각의 API를 사용한다.
- 네트워크 오류, 401, 서버 5xx, 평가 중복 제출을 사용자가 이해 가능한 방식으로 처리한다.
- 로그인, 평가 요청, 결과 표시, 프로필 수정의 자동화 테스트가 CI에서 실행된다.

| P2 | 요구사항이 모든 전이 의존성을 고정한 대형 목록이며 중복 항목도 있다. | 보안 패치·재현 가능한 빌드 관리가 어려움 | 직접 의존성과 lock 파일을 분리하고 Dependabot/Renovate 및 정기 취약점 스캔 도입 | 패키지 관리 도구 선택 | 1~2일 |
| P2 | 정적 프로필 파일이 애플리케이션 컨테이너/호스트 볼륨에 결합되어 있다. | 인스턴스 교체·다중 인스턴스에서 파일 접근 불일치 | S3 호환 객체 스토리지, CDN, lifecycle 정책, 업로드 바이러스 검사(필요 시) 도입 | 스토리지 계정·보존 정책 | 3~5일 |

### Infra 권장 완료 기준

- 새 개발자는 문서화된 compose 명령으로 앱과 DB를 재현할 수 있다.
- 프로덕션 DB는 인터넷에 직접 노출되지 않는다.
- 배포 파이프라인은 테스트·이미지 검사·health check·롤백 가능한 SHA 태그를 포함한다.
- 백업 복구를 최소 1회 실제로 검증하고, 장애/성능 지표에 알림이 연결된다.

## 단계별 실행 계획

### 0단계 — 즉시 위험 제거 (3~5일)

1. Flutter의 TLS 인증서 우회와 하드코딩 HTTP URL을 제거한다.
2. 백엔드 JWT 인증 의존성과 리소스 소유권 검증을 모든 개인 API에 적용한다.
3. CORS를 환경별 허용 목록으로 제한하고, 앱 번들에서 비밀값을 제거한다.
4. 외부에 노출된 DB 포트를 제거하고 배포 환경의 접근 규칙을 확인한다.

### 1단계 — 핵심 흐름 안정화 (6~10일)

1. 평가 저장을 하나의 transaction으로 바꾸고 idempotency를 적용한다.
2. 프런트/백의 공통 오류 형식과 timeout, 재시도, 401 처리 정책을 확정한다.
3. 이미지 실제 형식 검증 및 업로드 제한을 적용한다.
4. health/readiness endpoint, 구조화 로그, 백업 일정을 구성한다.

### 2단계 — 품질과 배포 기반 (8~13일)

1. Flutter와 FastAPI의 핵심 흐름 자동 테스트를 만든다.
2. CI에서 lint/test/build/image scan을 통과해야만 이미지가 배포 후보가 되게 한다.
3. compose와 환경변수 문서를 정리하고 migration을 배포 작업으로 분리한다.

### 3단계 — 구조/성능 확장 (12~20일)

1. 평가·인증·학습·콘텐츠 생성 모듈을 모듈러 모놀리스 구조로 정리한다.
2. 평가 시간, 대기열 길이, 오류율을 측정한다.
3. 기준을 넘는 경우 OCR 평가를 큐 기반 워커로 분리하고 상태 조회 API와 앱 진행 화면을 추가한다.

## 워커 분리 의사결정 기준

다음 중 하나가 1~2주 이상 지속될 때 비동기 평가 워커를 우선 도입한다.

- 평가 API의 p95 응답 시간이 제품 목표(예: 5초)를 초과한다.
- 평가 요청 중 타 API의 p95 지연 또는 오류율이 눈에 띄게 증가한다.
- 동시에 2건 이상 평가할 때 CPU/메모리 포화가 반복된다.
- 평가 재시도·작업 추적·오프라인 복구 요구가 제품 요구사항이 된다.

그 전에는 모듈러 모놀리스와 단일 트랜잭션, 측정 지표를 먼저 갖추는 편이 구현·운영 비용 대비 효과적이다.

## 확인이 필요한 의사결정

- 웹 클라이언트도 운영할지, 앱 전용인지에 따른 CORS 및 인증 정책
- 프로덕션 도메인, TLS 종료 지점, staging 환경 유무
- 개인정보 보존 기간과 프로필/손글씨 이미지의 저장 정책
- 평가 완료 목표 시간, 예상 동시 사용자·일일 평가량
- 객체 스토리지·모니터링·큐 운영 예산과 담당자
